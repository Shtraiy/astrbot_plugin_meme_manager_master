# README 风格规范

这套风格适用于 AstrBot 插件或其他中文开源项目 README，目标是让文档更清晰、更有项目辨识度，同时尽量保留原有功能说明。

## 一、整体风格

- 使用中文作为主要说明语言，命令、配置项、路径和代码保持原样。
- 结构清晰，先介绍项目，再说明功能、使用方式、配置和开发验证。
- 视觉上简洁但有层次感，适度使用 emoji、徽章、引用块和表格。
- 以“调整排版为主、少改正文为辅”为原则，不为了追求样式而重写项目说明。
- 所有版本号、依赖版本、功能描述和链接都必须来自项目实际信息，不编造不存在的能力。

## 二、顶部项目区

使用 HTML 将项目标题、徽章和 tagline 居中：

```html
<div align="center">

# 项目名称

[![version](https://img.shields.io/badge/version-v1.0.0-blue.svg)](项目主页)
[![AstrBot](https://img.shields.io/badge/AstrBot-%3E%3D4.5.7-orange.svg)](https://github.com/Soulter/AstrBot)

**一句话说明项目价值或使用场景**
</div>
```

### 徽章规则

- 优先展示版本、兼容平台或框架、许可证等真实信息。
- 版本号应与项目元数据保持一致。
- 徽章数量保持克制，通常 2–4 个即可。
- 徽章链接应指向项目主页、许可证文件或对应官方页面。
- 如果无法确认某项信息，就不添加对应徽章。

## 三、开场介绍

顶部项目区后使用引用块概括项目：

```markdown
> **project-id** 是一个基于 AstrBot 的……插件，提供……能力。
```

建议在一段话内回答三个问题：

1. 这是什么项目？
2. 它解决什么问题？
3. 它有哪些核心能力？

如果项目存在兼容性、迁移或共存说明，可以紧跟一个提示块：

```markdown
> [!NOTE]
> 本插件使用独立的数据目录，可以与原版插件并存；详细迁移规则见下文。
```

提示块只放重要的前置说明，不重复大段正文。

## 四、章节标题

一级章节使用 `##`，并配合一个含义明确的 emoji：

```markdown
## 📌 主要能力
## 🖥️ WebUI
## 📦 数据结构
## ⚙️ 配置
## 🧰 可选依赖
## ✅ 开发与验证
```

### 标题建议

| 内容 | 推荐标题 |
| --- | --- |
| 功能概览 | `📌 主要能力` 或 `✨ 功能亮点` |
| Web 页面 | `🖥️ WebUI` |
| 文件和数据目录 | `📦 数据结构` |
| 配置项 | `⚙️ 配置` |
| 安装依赖 | `🧰 可选依赖` 或 `📦 环境依赖` |
| 测试与开发 | `✅ 开发与验证` |
| 使用命令 | `📌 核心命令` |
| 图片或界面展示 | `🖼️ 效果示例` |

emoji 用于区分章节，不要在每一行正文中滥用。

## 五、功能列表

功能概览优先使用短句列表，每条只表达一个能力：

```markdown
- 在 AstrBot WebUI 中直接管理插件数据。
- 按分类浏览、上传、删除和移动图片。
- 支持多 pack、默认包和会话选包规则。
- 自动识别群聊图片并按场景分类保存。
```

具体操作、命令和参数较多时，再使用表格展开，不要把所有细节堆在列表中。

## 六、命令和配置表格

表格适合表达固定字段之间的对应关系：

```markdown
| 命令 | 功能 | 参数 | 示例 |
|:-----|:-----|:-----|:-----|
| `/example` | 执行某项操作 | `<参数>` | `/example demo` |
```

推荐遵循以下规则：

- 命令、配置项、路径和参数名使用反引号。
- 表头字段保持简短，说明过长时放到表格下方补充。
- 示例必须与实际命令格式一致。
- 默认值、可选值和范围写清楚。
- 配置项很多时，README 只保留重点，详细配置链接到单独的配置文档。

## 七、目录结构和代码块

目录结构使用 `text` 代码块，保持缩进和层级：

```text
AstrBot/data/plugin_data/example/
└── packs/
    └── <pack_id>/
        ├── manifest.json
        └── memes/<category>/
            └── index.json
```

命令使用对应语言或 shell 代码块：

```bash
python -m unittest discover -s tests -v
python -m compileall -q .
```

代码块中的命令必须能够直接复制使用；如果命令依赖特定目录、环境变量或额外依赖，应在代码块前说明。

## 八、图片和效果展示

如果项目有真实截图或渲染结果，可以使用表格并排展示：

```markdown
| 默认风格 | 紧凑风格 | 海报风格 |
|:---:|:---:|:---:|
| <img src="path/to/default.png" alt="默认风格示例" width="240"> | <img src="path/to/compact.png" alt="紧凑风格示例" width="240"> | <img src="path/to/poster.png" alt="海报风格示例" width="240"> |
```

- 只展示仓库中真实存在或可以稳定访问的图片。
- 每张图片都写清楚 `alt` 文本。
- 图片宽度保持一致，避免撑破页面。
- 没有真实素材时不要为了凑版式添加占位图。

## 九、文字与排版

- 介绍性段落控制在 1–3 句，避免一段塞入过多并列信息。
- 章节之间保留一个空行，表格和代码块前后也保留空行。
- 专有名词、项目 ID、API、文件名和命令保持原文格式。
- 中文正文使用中文标点；代码、路径和 URL 使用英文字符。
- 同一概念始终使用同一个名称，例如不要交替使用“表情包包”“pack”“数据包”而不作说明。
- 说明“不会做什么”时，应明确限定范围，避免模糊表述。

## 十、改写边界

参考其他 README 调整样式时，默认采用保守改写：

- 可以调整：标题层级、emoji、徽章、引用块、提示块、空行、表格对齐和段落顺序。
- 可以微调：明显重复、语病、标点和过长句子的衔接。
- 不应随意调整：功能范围、配置默认值、命令格式、目录路径、迁移规则和依赖要求。
- 不应新增：项目没有实现的功能、未经确认的版本信息、虚构截图或未经验证的安装步骤。
- 自动生成的文件（例如索引 README）不应手动修改，除非用户明确要求。

## 十一、推荐骨架

```markdown
<div align="center">

# 项目名称

徽章

**一句话 tagline**
</div>

> **project-id** 是……

> [!NOTE]
> 重要兼容、迁移或使用提示。

## 📌 主要能力

- 核心能力 1
- 核心能力 2

## 🖥️ 使用方式

安装、入口或命令说明。

## 📦 数据结构

目录树和迁移说明。

## ⚙️ 配置

关键配置表格，并链接详细配置文档。

## 🧰 可选依赖

运行环境和额外依赖。

## ✅ 开发与验证

测试、检查和开发约定。
```

## 十二、提交前检查清单

- [ ] 顶部标题、徽章和 tagline 是否居中且信息真实？
- [ ] 开场是否在一段话内说明项目定位和核心价值？
- [ ] 章节标题是否使用统一的 emoji 风格？
- [ ] 命令、配置项、路径和代码是否使用反引号？
- [ ] 表格、目录树和代码块是否可以直接阅读或复制？
- [ ] 图片链接、跳转链接和 `alt` 文本是否有效？
- [ ] 是否保留了原有功能和配置说明？
- [ ] 是否误改了自动生成文件？
- [ ] 是否运行 `git diff --check` 检查空白字符问题？
