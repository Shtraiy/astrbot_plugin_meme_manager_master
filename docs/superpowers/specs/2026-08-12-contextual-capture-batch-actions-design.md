# 表情索引卡片上下文批量处置设计

## 目标

让批量选择后的处置入口直接位于卡片上，移除工具栏中冗余的“统一处理”按钮。用户点击任意已选卡片的处置按钮时，只批量处理与该卡片同一区域的已选项目，避免待处理项与已整理项被混合处置。

## 交互规则

- 未开启批量选择时，卡片上的“删除并拉黑”或“忽略并拉黑”只处理当前卡片。
- 已开启批量选择，但点击未选中卡片的处置按钮时，仍只处理当前卡片。
- 点击已选中的待处理卡片“忽略并拉黑”时，统一处理所有已选待处理项：
  - 普通待分类项删除未分类文件、忽略活动并加入永久黑名单。
  - 重复项忽略重复活动并加入永久黑名单，保留资源包中的已有图片。
  - 已选的已整理项不进入请求、不取消选择。
- 点击已选中的已整理卡片“删除并拉黑”时，统一处理所有已选已整理项；已选的待处理项不进入请求、不取消选择。
- 确认框只统计本次同一区域将要处置的项目。成功项取消选择，失败项继续保持选中并显示失败状态。
- 两个区域原有的“当前页/当前视图全选”和“清空选择”继续保留。

## 页面与代码边界

- 从 `pages/semantic/index.html` 和 `pages/a_manage/semantic/index.html` 删除 `capture-dispose-selected-button`。
- 两套 `semantic/script.js` 不再查询、更新或绑定该按钮，也不保留仅供该按钮调用的 `disposeSelectedItems`。
- 新增一个纯选择过滤逻辑：依据被点击卡片的 `kind`，从 `selectedItems` 中提取 `indexed` 或非 `indexed` 项；只有批量模式已开启且被点击卡片自身已选中，才使用过滤后的批量集合，否则使用单项集合。
- 继续复用现有 `disposeCaptureItems`、确认弹窗、`capture/items/dispose` 接口、完整工作区刷新和部分失败保留逻辑；后端接口与数据格式不变。
- 两套页面保持相同行为，同时保留各自原有导航与资源缓存差异。

## 边界与失败处理

- 通过 `selectionKey` 判断被点击卡片是否已选，避免仅依据 DOM class 导致状态漂移。
- “待处理”批量集合包含 `pending` 与 `duplicate`，但绝不包含 `indexed`；“已整理”集合只包含 `indexed`。
- 如果过滤后没有项目，则回退为当前卡片单项处置，不发送空请求。
- 处置进行中沿用全局禁用状态，防止连续点击产生并发请求。
- API 失败时现有选择状态保持不变；部分成功时只有后端返回的成功项从选择中移除。

## 测试与验收

- 静态页面契约验证两套 HTML 均不再包含 `capture-dispose-selected-button`，脚本不再包含 `disposeSelectedItems`，但仍保留三种卡片处置行为。
- JavaScript 运行时回归验证：
  - 已选待处理卡片按钮提交全部已选 `pending` 与 `duplicate`，不提交已选 `indexed`。
  - 已选已整理卡片按钮提交全部已选 `indexed`，不提交已选待处理项。
  - 未选卡片按钮与非批量模式仍只提交当前一项。
  - 同类批量部分失败后，失败项保持选中；异类选择始终保持选中。
- 修改后的全部 JavaScript 通过 `node --check`，并运行目标回归、全量 `unittest`、`compileall`、配置 schema、架构检查和 `git diff --check`。
- 在可用的 AstrBot WebUI 中人工确认桌面端与移动端按钮点击、确认文案、选择保留和处理中禁用状态。
